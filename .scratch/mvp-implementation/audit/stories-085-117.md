# Semantic audit: implementation stories 85–117

**Scope.** This audit compares each of stories 85–117 in the MVP implementation specification with the sequentially numbered acceptance-criteria bullets in all 20 implementation tickets. It also maps the related functional specification, resolved validation/runtime/schema architecture, and schema contract. “Explicit” means the ticket acceptance criteria state the behavior and include relevant evidence; “delegated-only” means a normative source binds the behavior but the acceptance criteria do not make the specific behavior testable; “ambiguous” means ticket wording can be read in a way that conflicts with or leaves the required behavior unclear; “missing” means no responsible ticket criterion or successor was found for a normative obligation. An AC number below is the ordinal of the bullet under that ticket’s “Acceptance criteria” heading.

This is a specification audit, not evidence that the MVP has been implemented. The ticket index says ready-for-agent means specification readiness. The three prototype verdicts reviewed below are architecture evidence for their stated small fixtures only; they do not establish production behavior.

## Resolved architecture mapping

### Issue 09: SHACL validation boundary

The decision makes validation target-scoped and offline. It requires target-owned shapes; effective ontology-associated shapes; and, for concrete models, shapes associated with referenced conceptual schemas. Each run gets the target’s data plus only explicit subclass/subproperty hierarchy from available ontology/schema graphs, with the necessary hierarchy also available in the shapes dataset for the selected validator. It excludes other model data, implicit entailment, consumer rebinding of locked models, and remote loading.

It also fixes the Core plus SHACL-SPARQL SELECT profile, prefix/PATH expansion checks, required outer SELECT projection of this, pre-binding restrictions, rejection of forbidden query forms before execution, whole-shapes-graph skipping for unsupported/unsafe content, independent continuation, no invented RDF-result source locations, shape-source attribution, and severity/status behavior.

**Owners:** 04 AC2–8, AC10–11; 09 AC3; 10 AC2–4, AC8; later category evidence in 13 AC10 and 14 AC9. Ticket 04 AC5 now names negative fixtures for PATH placement, missing this projection, forbidden query forms, MINUS/VALUES, AS rebinding, subqueries, and unbound shapesGraph/currentShape. AC10–11 and 13/14 assign distinct diagnostic kinds and classification/coverage evidence across resource families. These updates resolve the previously identified SHACL-form and diagnostic-category gaps; later source-bound and view/design scopes still require their assigned feature tickets to close.

### Issue 13: shared CLI and loopback web runtime

The decision separates transport-independent project operations from direct CLI and authenticated HTTP adapters. It specifies one fixed project server, exclusive protected registration, full process/protocol handshake, verified startup and reconnection, explicit foreground/background/detach/status/stop behavior, bounded redacted logs, Host/Origin checks, distinct native and browser credentials, single-use browser bootstrap, server-held reviewed previews, cancellation/retry boundaries, package compatibility, and cross-platform implementation evidence.

**Owners:** 02 AC3–10 owns runtime and browser security/lifecycle; 01 AC5–8 provides project operation coordination; 07 AC7–8, 08 AC9, 10 AC5–6 and 15 AC5 own feature previews; 20 AC1–10 owns packed-artifact and cross-platform evidence.

02 AC4 now spells out issue 13’s exceptions for missing Origin on legitimate same-origin reads and authenticated native controls, while requiring exact Origin for bootstrap and browser mutations. This resolves the identified wording ambiguity. Runtime security remains an early executable contract in ticket 02; it cannot be deferred to package verification in ticket 20.

### Issue 14: concrete file and output schemas

The decision makes the version-1 file/output contract normative and explicitly assigns runtime mechanics to issue 13 and concrete wire/path/field/fingerprint encodings to issue 14. It resolves exact schema version separation, selector delimiter, accepted-preview flag, JSON envelope/status/diagnostic structures, reusable records, managed-reference semantics, revisions and exact preview fingerprinting, impact comparison and coverage, transaction/runtime record formats, browser credential lifetimes, web response fields, and implementation evidence. No production implementation or runtime behavior is claimed by that architecture document.

**Owners:** 01 AC4–9; 02 AC1, AC5–10; 04 AC4–10; 06 AC5–6; 07–10 preview criteria; 12–19 resource records/extensions; 20 AC8–10. The schema is binding wherever an acceptance criterion says to use the version-1 contract. Several exact field names and precedence rules are delegated to the contract rather than repeated in each ticket; ticket 20 and the public-operation checks remain the evidence boundary. Pay special attention to the diagnostic and runtime field-level assertions described below.

## Closure and evidence boundaries

The issue README preserves all 20 approved tickets, distinguishes execution authorization from specification/dependency readiness, and says a story spanning tickets is complete only when all its mapped scope is complete. Writing/reviewing the breakdown authorizes only that documentary work; production implementation requires an explicit user instruction naming one ticket, a ticket set, or the full plan. Authorization covers the necessary implementation/checks/fixes within that scope, but finishing a ticket does not authorize the next one; publication/deployment remains separate. Ticket 01 owns the shared project-operation/locking foundation, not blanket proof for every feature. Tickets 02–19 must apply that foundation to enabled feature operations and add their own public-operation/adapter evidence. Later tickets explicitly own resource-kind extensions (for example, views in 13, designs/presentation in 14, deletion cleanup in 18, and refactor/repair/GC in 19). Ticket 20 depends on 01–19 and performs assembled scenario, package, and platform closure. Do not mark shared validation, CLI, guidance, safety, or story coverage complete based only on the first ticket that introduces the shared contract.

All security and mutation protections required by a ticket are in scope when that ticket enables the operation. Ticket 20 adds cross-platform proof; it does not postpone authorization, path confinement, revision binding, rollback/recovery, preview ownership, or offline behavior for earlier enabled operations.

The RDF engine, React Flow, and layout prototype verdicts were inspected as historical architecture evidence. Their results are limited to their recorded fixtures/environments. The verdicts expressly leave acquisition, production schemas, transactions, full forms, authentication, cross-platform behavior, large/variable content, and durable writes unproven. Ticket 20’s actual packed-artifact and OS checks are required before claims of completion.
