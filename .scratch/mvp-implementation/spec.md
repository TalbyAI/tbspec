# MVP Implementation Specification

Version: 0.1
Status: ready-for-agent

## Problem Statement

Project teams and coding agents need a local, versionable way to describe their domain with reusable ontologies and domain models. Editing disconnected RDF files alone makes it difficult to discover available vocabulary, understand relationships, maintain independent visual perspectives, validate constraints, and assess the impact of dependency changes or removals. External resources can change or disappear, and concurrent file edits can invalidate what a user reviewed before saving.

The repository has a closed functional specification and a resolved technical architecture, supported by isolated RDF-engine, canvas, and layout proofs. It does not yet contain the production CLI, shared project operations, or local web application. The next deliverable is an MVP implementing those agreed behaviors and contracts together, with reproducible local dependencies and consistent outcomes across both interfaces.

## Solution

Provide `tbspec`, a non-interactive CLI for project operations and automation, plus a local web interface for exploration and editing. Both interfaces operate on the same RDF/TOML project files through shared project operations. Users can manage ontologies and domain models, reuse locked dependency snapshots, validate their descriptions offline, explore read-only SPARQL results, and maintain multiple view models with independent presentation graphs.

New projects include locked, versioned resources for data, descriptive process, and descriptive state-machine modeling. Teams can replace or extend the available vocabulary without losing generic editing. Specialized forms recognize exact supported RDF terms and preserve other statements. Impact previews, explicit acceptance, content revisions, and staged file changes protect reviewed operations while still permitting deliberate changes that leave a project semantically invalid and in need of repair.

This specification synthesizes the existing product and architecture decisions. The linked source documents in Further Notes remain normative for exact command signatures, RDF terms, schemas, and detailed acceptance requirements. It introduces no additional product features or reopened architecture decisions.

## Implementation Decisions

1. **Delivery and shared operations.** Implement the agreed production CLI, project-operation core, Node server, and React interface as one application. Compile TypeScript to JavaScript. Ordinary CLI commands call transport-independent operations directly; authenticated HTTP adapters call the same boundary. Keep resource discovery, RDF operations, resolution, acquisition, impact planning, revisions, and transactions out of route handlers. Use one fixed project per server and fresh in-memory datasets per operation.

2. **Runtime and package baseline.** Use supported Node 24 LTS patches. Start with the proven direct versions: `n3` 2.7.12, `@comunica/query-sparql-rdfjs-lite` 5.4.1, `@comunica/utils-bindings-factory` 5.4.0, `@traqula/parser-sparql-1-1` 1.4.0, and `shacl-engine` 1.1.2. Add the approved `rdfxml-streaming-parser` 3.3.0 for narrow RDF/XML acquisition. Pin the application's transitive dependencies. Use React, React Flow, a Vite-built static interface, and `elkjs` 0.12.0; the architecture does not select TanStack Start or a persistent RDF database.

3. **Canonical project and file schemas.** RDF/Turtle authoring files and the versioned TOML manifest, dependency lock, and saved-query declarations are canonical. Implement the independent version-1 schemas and compatibility rules already settled. Reject unsupported required versions and unknown semantic lock/query fields; preserve and ignore unrelated manifest fields. Keep package, vocabulary-release, project-file, JSON, record, and control-protocol versions independent. Package upgrades perform no implicit migration or dependency update.

4. **Selectors and identity.** Separate project-relative file selectors, dependency IDs, retained inventory selectors, source locators, and RDF IRIs. Locked graph selectors use `dep:<id>` or `dep:<id>/<file-key>`; administration uses the bare ID. Declared managed roots retain their original graph IRIs. Generate an unrooted graph's project-local identity from the SHA-256 of its canonical expanded selector and disclose changes caused by moving or renaming it. Validate portable path/ID grammar and identity collisions; listings supply the exact selectors accepted by later operations.

5. **Classification and model associations.** Classify ontologies through their root's `owl:Ontology` declaration and models/support through the settled metadata classes. Choose the most specific compatible kind; diagnose incompatible kinds or distinct candidate roots. Individual business types do not become graph roots. Owned model roots record their configured model-type name. Concrete models may explicitly reference conceptual schema models; their own selected ontology stays available. Locked models retain source bindings and never resolve a source type name through the consuming manifest. Unclassified parseable graphs remain generically editable.

6. **Configuration and lifecycle.** Implement the complete functional command inventory and its web operations for configuration, ontologies, models, schemas, views, designs, shapes, dependencies, queries, impact, repair, and garbage collection. Initialization supports upward discovery, an explicit root, and optional base IRI without requiring Git. Creation refuses occupied destinations and requires a supplied or derivable identity. Editable imports assign new graph-root identities and provenance while preserving term identities. Moves update owned path associations and convention-linked support without silently changing declared IRIs.

7. **Model-type changes.** Offer locked data/process/state-machine defaults and custom types. Disabling retains existing bindings and validity. Reset restores the project's locked default row; built-in types are disabled rather than removed. Replacing a used ontology previews impact and requires acceptance, leaves model files unchanged, and disconnects the previous design. A replacement configuration row does not inherit the old design field. Explicit design selection may reuse a supplied design for a compatible local copy; no term mapping or automatic migration is performed.

8. **Permanent vocabulary and bundled resources.** Author immutable first releases of the metadata, process, and state-machine ontologies under the approved `https://talby.ai/ontology/` identities, stable `#` terms, and version `0.1.0`. Use the settled exact metadata, view, presentation, visual-rule, process, state, and SHACL identities and constraints. Bundle standard vocabulary definitions, attributed P-Plan 1.3, shapes, designs, original parser contexts, and verified digests. The default data association uses the metadata starter plus standard RDF/RDFS/OWL vocabulary rather than a fourth tool-owned namespace. Initialization locks the common metadata contract independently of model-type replacement and copies resources offline.

9. **Starter semantics.** Keep process and state-machine models descriptive. P-Plan uses its pinned `isPrecededBy` spelling; do not map the older spelling. Shared plan memberships, optional conditions, cycles, self-flows, and unfinished decisions are allowed; input/output variables share a plan with their step and have at most one distinct producer. State constraints enforce machine ownership, matching endpoints, at most one initial state, and no outgoing transition from a final state. Empty machines, cycles, self-transitions, and an initial-plus-final state are permitted. Do not add execution, reachability, determinism, or completeness requirements.

10. **Acquisition adapters and closure.** Directory, installed Git, HTTP(S), and packaged bundle acquisition produce original bytes and interpretation metadata without mutating the consumer. Include only the selected resource's discoverable interpretation closure, directly associated support, and relevant source choices. Follow recorded ontology/import/schema/vocabulary edges with cycle detection; source-project locked files are copied without refetching. Do not include unrelated models, upstream views/presentations, or queries. A missing, corrupt, unsupported, or unparsable declared included file rejects acquisition; unresolved IRIs in otherwise parseable resources remain diagnostics. A standalone URL is one graph and is never recursively crawled.

11. **Acquisition restrictions.** Canonicalize and confine directory discovery, rejecting internal links and escaping metadata. Capture cooperating source projects under their read lock without holding a consumer lock simultaneously. Resolve Git once to an immutable commit, read raw tree/blob data in private temporary storage, disable hooks/filters/submodule and LFS execution, and invoke argument arrays without a shell. Require Git only for explicit Git actions. Persist credential-free locators and redact secrets. Enforce the approved configurable limits during acquisition: 64 MiB per graph, 256 MiB included bytes, 1,000 files, five redirects, five minutes overall, and a best-effort 1 GiB Git workspace. Cancellation and acquisition failures publish nothing.

12. **Parsing and snapshot integrity.** Allow strict single-graph Turtle, N-Triples, and the conservative local RDF/XML profile. Preserve original bytes, media type, effective base, parser profile, and graph-scoped blank-node identity. Reject dataset serializations, remote contexts, arbitrary DTD/entity declarations, and external entity resolution. Only exact vetted bundled P-Plan bytes may use the agreed internal-entity exception. Verify local bytes and reconstructed signatures before use; corruption never authorizes a network repair. Implement XML-aware rejection and demonstrate the parser's local behavior before claiming RDF/XML support.

13. **Lock inventory and drift.** Record per-file keys, byte digests, graph signatures, parser context, roles, provenance, resolution contexts, edges, model bindings, support, choices, and attachment activity under the concrete lock contract. Graph equality depends on bytes and parser context; aggregate interpretation signatures additionally include reachable associations and choices. Use the specified canonical JSON hashing and golden vector, without RDF canonicalization. Included formatting or interpretation changes are drift; unrelated commits/settings and consumer-ID relocation alone are not. Check is read-only and distinguishes changed/partial comparison from unavailable sources. Independently added snapshots remain independent; no shared content store is needed.

14. **Ontology and design resolution.** Resolve ontology candidates by IRI and graph signature: explicit consuming choice, owned ontology, direct dependency, then nearest transitive dependency by shortest path. Equal content is one effective candidate with retained provenance/support contexts; different-content winning ties are errors. Register only the winner and its effective support in a full-project dataset, retaining losing files for isolated access under original IRIs. Locked models validate in their recorded source context. Resolve whole designs separately per exact target: explicit consuming choice, owned design, design associated with the effective ontology, then nearer inherited designs. Report ties, broken choices, and divergent non-ontology graph identities; never merge losing triples or competing appearance fields.

15. **Dependency updates and attachments.** Preview source, resolution, and downstream validation changes against the captured baseline. Newly introduced/worsened invalidity or unavailable impact assessment requires update impact acceptance; acquisition/parse failures cannot be bypassed. CLI add/update/support application binds reacquired bytes to an accepted fingerprint. Manual support remains separately recorded across main-source updates; clearing deactivates an association and retains its files. Deduplicate equal shapes, run distinct active associated shapes separately, and resolve all designs through normal precedence. Dependency renames preserve declared RDF identities and content; confirmed removal affects only the selected addition's managed inventory, leaving other snapshots and owned references intact.

16. **Query assembly and isolation.** Fully parse required files before registration. Full-project queries load the effective registry as named graphs and copy only effective ontology/model triples into the default graph; support and unclassified graphs remain named-only. Unresolved ontology choices, genuine loaded IRI collisions, or required malformed graphs fail with affected selectors. A selected-graph query loads only that resource, including retained losing/support files, as both default and sole named graph; unrelated invalid files and consumer resolution conflicts do not block it. Keep Comunica's union-default option disabled and do not add inferred triples.

17. **Queries and parameters.** Gate every user and SHACL-SPARQL query through the parsed AST before engine invocation. Accept only read-only SELECT, ASK, CONSTRUCT, and DESCRIBE for user queries; reject Update, nested SERVICE, FROM, and FROM NAMED. Engines receive only local in-memory RDF/JS sources. Validate saved declarations and JSON RDF-term bindings before supplying typed initial bindings, never text interpolation. Preserve literal language/datatype, unbound SELECT cells, result-scoped blank nodes, ASK false success, and graph results under the output contract. Optional hierarchy exploration uses explicit SPARQL property paths, with no general entailment or persisted inferred statements.

18. **Validation data and diagnostics.** Run syntax, classification, vocabulary, association, view, presentation, and applicable SHACL checks with distinct codes. Each target/shapes run receives only the target's own triples and the explicit subclass/subproperty hierarchy from its effective vocabulary and conceptual schemas. Supply that hierarchy to the selected validator's shapes dataset as required for class checks; add no other model data or inferred types. Apply target-owned, effective ontology-associated, and concrete-model schema-associated shapes separately and attribute every result to its source. Selected-resource validation loads its prerequisites rather than downstream dependents. Full validation includes retained snapshot integrity/syntax and source-bound model validation.

19. **SHACL profile and partial coverage.** Support Core and `sh:sparql` SELECT constraints. Diagnose unsupported SPARQL targets/components. Validate prefix/PATH expansion, required `this` projection and pre-binding restrictions, and reject forbidden query forms before execution; unsupported or unsafe shapes are skipped as a whole. Independent valid shapes/resources continue. Missing required vocabulary/support blocks dependent checks with explicit skipped diagnostics rather than an incomplete clean pass. Map SHACL Violation/Warning/Info to error/warning/info; warnings alone do not fail validation. Do not invent source locations. Ordinary external data-value IRIs are neither broken managed references nor fetch instructions.

20. **Direct RDF canvas projection.** Project IRI/blank-node subjects and resource-valued objects as nodes, and each resource-valued source triple as an exact edge. Show literal statements in a term-level properties panel, retaining unknown structural statements. Generic and specialized edits share add/remove/replace operations and preserve unknown statements, language, and datatype. Blank nodes are editable in the complete graph but are not stable saved-view members. Flow and Transition remain resources with ordinary RDF edges, rather than collapsed semantic connections. Raw source saves preserve submitted text and can be syntactically invalid; graph operations require every rewritten graph to parse.

21. **Views and presentations.** A view references one source and selects IRI members plus exact source relationship tuples with both IRI endpoints. Relationship identity includes source, subject, predicate, and object; descriptors do not assert source triples. Each view has its own linked presentation, with paired finite absolute coordinates, local style, flat grouping, and applicable exact-type rule choices. Resource addition includes existing relationships to already selected members. View-only removal clears its local incident selections and presentation without touching source/other views. Graph-based source relationship replacement/deletion synchronizes all affected views/presentations; direct Turtle edits leave their files unchanged and report broken references. Complete-graph and generated missing positions remain temporary until explicitly saved.

22. **Visual rules.** Implement the exact supported node/edge fields, enums, label resolution, numeric guards, and initial design rules from the starter contract. Render through fixed components and typed assignments; no arbitrary CSS, HTML, scripts, URLs, fonts, or executable project components. Designs target exact class/property terms without hierarchy inheritance. A per-view chosen rule must belong to the winning design for an explicit type and cannot select a losing design. Missing coverage or unchosen competing exact-type rules uses generic appearance with a canvas warning, not model invalidity. Broken persisted presentation choices receive presentation diagnostics.

23. **Layout and exploration.** Use ELK layered/RIGHT with stable RDF-term ordering, a fixed seed, real node dimensions, and a dedicated browser worker. Initial layout applies when no positions exist; incremental placement fills only missing positions near neighbors without moving valid existing coordinates. Reorganize previews all active-canvas positions and applies only its presentation, leaving source, membership, and other views unchanged. Cancel/failure retains prior positions; an initial failure provides a temporary deterministic grid, diagnostic, and retry. Reject stale worker results/previews. Search labels/full IRIs, center and highlight neighbors, and provide navigable exact incoming/outgoing triples, separate parallel predicates, and self-loops. Viewport culling never removes search/navigation membership. Persist no camera or algorithm-option schema.

24. **Specialized forms and lossless values.** Select ontology, conceptual-data, process, and state-machine form families from valid graph classification and exact explicit recognized types. Use the settled OWL/RDFS, pinned P-Plan, process, and state terms; no aliasing through names, visual designs, subclass inference, or older spellings. Expose all applicable sections and every existing value, including incompatible types/cardinality violations. Keep unsupported structures accessible generically without coercion. Ontology/conceptual forms share class/datatype/property bindings; ontology individuals use the agreed individual fields. Concrete/custom/unclassified models remain generic. Retain recognized existing data with diagnostics when vocabulary is missing, but offer creation only from available terms.

25. **Form mutation, creation, and deletion.** Unchanged fields do not regenerate resource statements. Lexical-only literal edits retain language/datatype. P-Plan forward/inverse input/output statements display as one association; additions write only Step-to-Variable, and explicit association removal deletes both existing directions in that source. Creation writes only selected types/values and explicitly selected plan/machine memberships/endpoints, without superclass/inverse/optional materialization. Keep Add triple separate from Create flow/transition. Element deletion previews and confirms all subject/predicate/object occurrences in its source, synchronizes affected views/presentations, and leaves other graphs' references diagnosed but untouched. No recursive connected-resource deletion; managed root deletion uses lifecycle operations and identity change uses refactoring.

26. **Impact, repair, and deliberate invalidity.** Resource deletions and schema removal preview affected references and require confirmation. Refactoring and scoped dangling-reference redirection/removal preview by default and require application; IRI refactoring rejects conflicting owned declarations and never edits locked bytes. Garbage collection considers only orphaned owned support of removed sources and requires named candidates or all, plus apply and confirm; independent designs and dependencies need their own removals. Allowed accepted mutations may leave semantic errors: report resulting validity, treat the completed mutation as successful, and let later status/validation expose invalidity. Required malformed graphs must be repaired in source before graph-based bulk mutation.

27. **Coherent snapshots and ownership.** Use one short-lived exclusively created operation lock per canonical project for cooperating CLI/web reads and commits. Capture needed bytes/inventories together, release for computation/acquisition/review, and reacquire to commit. Busy contenders fail immediately without altering a partially initialized owner record. Verify acquisition token, host/boot, PID, and process-start identity; do not use age or PID alone. Ownership-write/close failure changes no canonical files and releases only when token ownership is established. Unknown/abandoned operation locks or pending transactions require manual recovery, never automatic clearing. Different projects remain independent.

28. **Publication, revisions, and confinement.** Plans bind exact read/destination bytes or absence and relevant directory inventories using SHA-256. Recheck under the lock and immediately before filesystem actions; a changed accepted plan aborts rather than silently replans. Prepare proposed bytes, before-images, and progress records on the same local filesystem before native replacement. Guard reverse rollback against intervening external edits. Preserve recovery evidence and block normal operations after interruption/incomplete rollback; completed cleanup failure is success with warning. Confine owned writes, reject traversal/drive/UNC/alternate-stream paths, internal links/junctions, multiply linked writable files, and platform-equivalent collisions. Surgically edit human TOML and reparse it; graph serialization preserves RDF semantics rather than Turtle formatting/comments. The coordination contract covers ordinary local filesystems, not hostile writers or crash-atomic multi-file publication.

29. **CLI and machine contracts.** Implement exact functional signatures and version-1 command data, diagnostics, RDF terms, revisions, and preview shapes. Every JSON invocation, including argument errors/help/version, emits one envelope and no progress stdout. Preserve exit categories 0 success/preview, 1 invalidity/drift, 2 invalid arguments/query policy, 3 conflict/acceptance/recovery, and 4 unavailability/I/O, with settled precedence. Successful intentional semantic invalidation remains exit 0 with resulting validity. Non-interactive project commands retain explicit apply/confirm/accept-impact flags. An accepted fingerprint supplements those flags; CLI external-content application reacquires once, compares the regenerated fingerprint, then revision-checks before publishing. Provide recursive documentation-only agent guidance and command help without requiring a project for guidance/help/version.

30. **Loopback server and browser boundary.** Bind only to the explicit loopback host; authenticate project reads, mutations, long operations, and controls, and enforce actual Host/exact Origin checks without proxy trust or permissive CORS. Public assets contain no project data/secrets. Use distinct protected native-control and tab browser bearers, a single-use fragment bootstrap, and the settled token lifetimes. Render source/labels as text, serve assets locally, and acquire external content only through explicit dependency actions. Browser previews retain server-held exact staged bytes and expected revisions, are session/instance owned, expire after the disclosed lifetime, and are consumed on success or invalidated on cancel/restart/relevant changes. Uncertain transport outcomes require inspection rather than automatic write retries.

31. **Server lifecycle and distribution.** Start a separate Node process without terminal dependency or visible background window and enforce exclusive per-project runtime registration with authenticated full-identity/protocol handshake. Foreground means an attached bounded log/control console; background/JSON startup returns readiness without attachment. Detach or unexpected terminal/browser disconnection preserves the server, sessions, and unexpired previews; Ctrl+C or authenticated stop requests graceful shutdown. Status never starts/attaches; absent stop is idempotent. Verify ownership before cleanup/control and refuse incompatible protocols or explicit-port conflicts. Keep controls responsive, using bounded Node workers for CPU-heavy RDF work where needed. Distribute one npm artifact containing compiled application, prebuilt matching assets, and verified immutable starter inventory; installed operation needs Node, with Git optional only for Git acquisition. External publication/deployment is a separate release action.

## Testing Decisions

1. **Primary seam.** Test public shared project operations against temporary on-disk projects, asserting returned records, diagnostics, accepted impact, and resulting file bytes/RDF terms. This is the main integration boundary for discovery, configuration, lifecycle, parsing, resolution, query, validation, editing, repair, and publication. Prefer complete user workflows to separate private parser/store/route mocks. A good test distinguishes a specified outcome or failure from an incorrect one; it does not assert internal helper calls, module layout, framework state, or incidental Turtle ordering.

2. **Necessary adapter coverage.** Add CLI process checks for command signatures, selectors, non-interactivity, one JSON envelope, stderr separation, stable exit/status categories, recursive guidance, and every public command family's routing. Add real HTTP/browser checks for authentication, bootstrap, view/form/canvas interactions, drafts, layout, and lifecycle behavior that the core alone cannot establish. Keep these focused on adapter and interaction contracts rather than repeating every core permutation. The user explicitly confirmed the shared-core boundary with CLI and browser checks on 2026-10-04.

3. **Project lifecycle and original acceptance scenarios.** Turn all seven functional acceptance scenarios into executable workflows: project/conceptual/concrete creation and schema references; external ontology acquisition/check/update; accepted vocabulary replacement; independent views/design ties; retained ontology-version conflicts; breaking removal/repair/GC; and malformed RDF with isolated query/partial diagnostics. Extend them with the resolved architecture contracts rather than treating the earlier examples as exhaustive.

4. **Schemas and preservation.** Exercise unsupported/missing versions, portable selectors/IDs, retained-file access, generated-identity relocation, effective defaults, disable/reset/design disconnection, malformed lock records, saved parameter declarations, and exact typed JSON results. Check manifest and query-declaration unrelated bytes/comments/line endings across surgical edits. Verify canonical hash golden vectors, Unicode/null/set ordering, graph equality versus interpretation drift, and signature stability under consumer ID changes. Verify RDF semantics across graph serialization while raw source saves retain submitted text.

5. **Resource contracts and constraints.** Use valid and invalid fixtures for each bundled vocabulary, shapes, and design release. Check exact identities/hierarchies, empty valid starters, most-specific classification, root ambiguity, optional schemas, view tuple uniqueness/endpoints, presentation duplicates/paired negative coordinates, finite style conversion, label-mode inheritance, and winning-rule applicability. Cover P-Plan inverse inputs/outputs, shared-plan flows and distinct producers; state cycles, initial-plus-final states, wrong-machine transitions, multiple initials, and final outgoing transitions. Run every bundled supported Core/SELECT constraint offline; resource authoring is production work still to be done.

6. **Local query behavior.** Exercise SELECT/ASK/CONSTRUCT/DESCRIBE, typed/language parameters, omitted unbound cells, graph/result-scoped blank nodes, ASK false, default-union exclusions, exact named identities, and isolated default/named access. Show that losing ontology content is excluded from consumer assembly but available by retained selector. Required malformed files, unresolved choices, and genuine loaded collisions must fail while unrelated malformed resources do not block a selected graph. Verify forbidden top-level/nested query forms are rejected before engine/network execution, including after SHACL expansion; observe zero query/validation/render acquisition requests.

7. **Validation contexts and partial results.** Verify target-only data plus explicit vocabulary hierarchy, source-bound locked models, deduplicated shapes and separate source attribution, selected-resource prerequisite scope, and no inferred persistence. Exercise unsupported SHACL forms, PATH/pre-binding restrictions, unsafe/malformed shapes, malformed required ontology/schema files, and continued independent checks. Assert explicit blocking/skipped coverage, no invented locations, correct severities, and warning-only success. Ordinary external individual IRIs must not generate availability fetches.

8. **Dependency acquisition and drift.** Use controlled directory, Git, and local HTTP fixtures. Verify selected closure only, cycles, source-snapshot reuse, original bytes/bases, declared-file rejection without replacing existing snapshots, standalone unresolved associations, safe redirects/credential redaction, limits/cancellation, missing optional Git, and excluded hooks/filters/LFS/submodules. Test vetted P-Plan RDF/XML without entity/network loading and reject modified DTD-bearing or dataset inputs. Compare included byte/binding/support/choice changes with irrelevant commits/configuration; check unavailable versus changed/partial outcomes without canonical writes. Manual attachments survive updates, inactive support remains retained but excluded from active interpretation, and independent additions never mutate one another.

9. **Revision-bound previews.** Verify local and acquired-content plans through their public preview/apply workflow. CLI reacquisition with the same fingerprint applies; changed bytes, parser context, support, output lock bytes, impact, inventory, or project root rejects without writes. Required flags remain independent of the fingerprint. Updates compare introduced/worsened impact against baseline errors. Browser application uses only server-staged bytes with owner/instance/expiry/fingerprint/revision checks, no refetch, and single successful consumption; detach preserves previews, while relevant change/cancel/restart invalidates them.

10. **Publication and failure evidence.** Inject failures at actual filesystem/process boundaries, including ownership-record write/close, staging, intermediate publication, rollback, and cleanup, while asserting through public operations and disk state. Require byte-for-byte restoration of normal replace/delete/move/lock failures, no canonical change before staging completes, protection of intervening external edits, retained originals/records and blocked operations after incomplete rollback/interruption, and success-with-warning after completed cleanup failure. These failure checks are essential evidence for the cross-file contract; do not infer atomicity from a passing happy path.

11. **Concurrency and filesystem support.** Use independent CLI/web processes to demonstrate immediate contention, an initializing ownership record left untouched while its holder completes, absent-destination and newly added reference/view conflicts, comment-only revisions, stale saves retaining drafts, and repeated conflict after reconciliation. Exercise PID reuse, unverifiable ownership, traversal, symbolic links/junctions, hardlinks, aliases, destination collisions, and permission/sharing errors. Execute platform-sensitive publication, ownership, confinement, acquisition, package, and server lifecycle checks on Windows, macOS, and Linux before claiming all three supported. Do not substitute same-process mocks for OS-sensitive evidence.

12. **Lossless forms and deletion.** Verify exact recognition in copied vocabularies without selected designs, arbitrary replacements, unavailable creation terms, multi-type sections, advanced blank-node OWL structures, and every existing invalid/multiple/language/datatype value. Unrelated edits preserve unknown statements. Exercise forward-only/inverse-only/both-direction P-Plan associations, creation without inferred materialization, and explicit Flow/Transition resources in the direct projection. Confirm element deletion's subject/predicate/object scope and coupled view/presentation cleanup while other source/locked references and unrelated coordinates remain unchanged. Test read-only snapshots and parseable-invalid versus malformed editing.

13. **Canvas, views, and layout.** In browser workflows verify complete graph/blank-node/literal projection, exact edge selection, endpoint membership, view-only versus source deletion, source synchronization, stale Turtle confirmation, and separate positions/rule choices. Test layout with 100- and 1,000-resource representative fixtures plus real dimensions, cycles, disconnected components, negative/sparse positions, parallel edges, self-loops, and dense hubs. Check existing-position preservation, initial fallback/retry, cancel/apply isolation, stale worker-result rejection, source/view preservation, and revision-checked persistence. Search and relationship navigation must reach off-screen resources without changing membership. Measure responsiveness; prototype timings are observations, not pass/fail performance budgets or maximum graph sizes.

14. **Web authentication and lifecycle.** Test authenticated Host/Origin checks, bearer separation, bootstrap replay/expiry, session expiry/restart, redacted/public responses, and safe text rendering. Require two concurrent starts to yield one verified server, independent projects, fixed roots, port conflicts, protected runtime registration, actual process/protocol handshake, unknown/unreachable states, version mismatch refusal, status without startup/attachment, and verified graceful/idempotent stop. Exercise foreground/background/JSON/non-TTY behavior, multiple consoles, detach/reconnect, unexpected terminal loss, browser closure, and cancellation during acquisition versus publication. Demonstrate responsive controls during long RDF work rather than inferring this from asynchronous APIs.

15. **Packed application and offline use.** Install and exercise the actual packed npm artifact, including compiled entry points, matching local assets/worker, license/source inventory, parser contexts, and bundled digests. Initialization, ordinary CLI queries/validation, and web rendering must work without network or development tools. Package upgrades leave project files/starters unchanged, locked reset restores the recorded version, and unavailable requested releases fail rather than substitute. Stop-before-replacement guidance and protocol compatibility must preserve the launched server release.

16. **Prior art and evidence limits.** The RDF-engine proof supplies integrated parsing/default-union/query-policy/typed-binding/Core-and-SELECT fixtures. The React Flow proof supplies a runnable projection and view-edit check with unknown-triple preservation. The layout proof supplies deterministic synthetic generators, position invariants, and separate recorded browser observations. Adapt these behaviors into production tests; their dependencies remain isolated and production cannot import the prototypes. There is no existing root production suite. Recorded prototype results establish only their stated fixtures and platforms, not the unimplemented acquisition, schemas, transactions, authorization, full forms, or cross-platform MVP.

## Out of Scope

- Git history/branching commands and a second revision or undo-history system; automatic ontology migration or mapping between incompatible vocabularies; CLI commands for individual RDF statement edits.
- Executable processes/state machines, hierarchical or parallel states, physical database schema generation, and built-in C4 or 4+1 protocols. Project-supplied protocol ontologies remain possible.
- A general form-definition framework, project-supplied executable visual plugins/components, arbitrary CSS/HTML/scripts/fonts, and automatic visual-rule inheritance through vocabulary hierarchies.
- SPARQL Update, SERVICE, remote dataset clauses, full RDFS/OWL reasoning, inference-dependent SHACL behavior, remote dereferencing during ordinary operations, and SHACL-SPARQL forms outside the agreed Core/SELECT profile.
- Multi-graph dataset imports, remote-context formats, general DTD-bearing RDF/XML beyond the vetted bundled exception, automatic remote import/SHACL expansion, Git submodules/LFS, and semantic-version solving.
- Saved-view source blank-node membership, persisted camera/layout-algorithm options, continuous automatic repositioning, required exploration filters, a second renderer, a persistent exploration index, or a persistent RDF database without new measured evidence.
- A shared dependency content store, silent cascading removal, detached-support auto-deletion, automatic crash replay/lock clearing, distributed coordination, guaranteed network-share behavior, adversarial same-user filesystem isolation, and multi-file crash or power-loss atomicity.
- New interviews, additional architecture discovery, rewriting the original functional specification or resolved map, and implementing production code during this specification-writing task. The implementation described here is the subsequent feature effort.
- Publishing an npm release, deploying an application, or configuring public vocabulary hosting during this task. Resource authoring, correct permanent identities, and offline bundling are implementation requirements; external publication is a separate release action.
