# Choose the shared CLI and loopback web architecture

Type: grilling
Status: ready-for-human
State: resolved
Assigned to: Codex
Blocked by: 05, 10

## Question

How will CLI commands and the local loopback web interface call the same project operations in the selected runtime, with the web session token and file-write boundary enforced? Decide the packaging shape for Windows, macOS, and Linux with at most one required installed runtime where practical, including bundling and explicit upgrades of versioned starter resources. Consider TanStack Start only if Node wins and only if it fits this local server boundary; keep route handlers out of the project core.

## Comments

- The user chose one fixed project per web server. Another project requires a separate server instance.
- The user requires foreground execution by default, optional background startup, reconnection to an existing background process, and the ability to move an already started foreground session into the background. The exact meaning of reconnection, lifecycle controls, and cross-platform process supervision remains under discussion.
- The user confirmed that reconnection means attaching a terminal control console with logs and controls to stop the server or leave it running in the background again. The server process and browser connections remain independent of console attachment.
- The user confirmed one web server per project. Running `tbspec web` for a project with an existing server reconnects to it instead of creating another server; different projects remain independent.
- [Runtime, packaging, lifecycle, and loopback security research](../research/cli-web-runtime-contract.md) records primary-source facts and architectural inferences. No production implementation or cross-platform lifecycle integration has been executed.
- The user approved Ctrl+C stopping the server, an explicit console detach action leaving it running, `tbspec web --background` for detached startup, and `tbspec web stop` for stopping an existing server. Closing a browser tab does not stop the server.
- The user approved one npm package requiring Node 24, containing the compiled CLI/server, prebuilt React/Vite interface, and immutable starter resources. Package upgrades do not update a project's locked resources.
- The user approved a React/Vite static interface with a local API and a shared project-operation core called by CLI and HTTP adapters, rather than TanStack Start for this MVP.
- The user approved session-token authorization for project reads, writes, and server controls, plus loopback binding and request origin/destination checks. Browser opening should provide an authentication bootstrap without manual token entry.
- The user approved keeping the server running after unexpected console disconnection. Explicit Ctrl+C or `tbspec web stop` stops it; detaching only disconnects the console.
- The user approved server-held previews containing exact acquired bytes and expected revisions. Console detachment preserves a preview; cancellation, server restart, or a relevant input change invalidates it and requires a new preview.
- The user additionally requires `tbspec web status` to report server state and URL without attaching a console.

## Answer

The user confirmed the interview decisions above and added non-attaching server status inspection. The contract below records those choices and the technical mechanisms derived from the existing security, dependency, and transaction boundaries. It specifies architecture and future acceptance evidence, not implemented behavior.

### Shared operations and runtime

- Use Node 24 LTS and the approved RDF package baseline. Compile TypeScript to JavaScript. Share a transport-independent project-operation module between CLI commands and the local server. The core owns resource discovery, RDF parsing/query/validation, dependency resolution/acquisition, impact planning, revisions, path confinement, and staged file transactions.
- Ordinary CLI operations invoke the core directly; they do not require a running web server or shell out through it. HTTP handlers authenticate, validate typed requests, call the same core, and translate results. Do not put project behavior in route handlers or expose arbitrary shell commands, filesystem paths outside the selected root, or a generic remote method dispatcher.
- Use React, React Flow, and a Vite-built static interface served alongside the API from one loopback origin. Keep filesystem, RDF engines, acquisition credentials, and transaction code on the Node side. Browser drafts and transient canvas state do not become authoritative project storage. Return projection/edit results and typed query/diagnostic data through explicit endpoints. TanStack Start is not selected: its documented server/SSR features do not justify the additional framework boundary for this local editor. Exact HTTP routing and client-state libraries are replaceable implementation choices.
- Take coherent snapshots and publish through the already approved short-lived cross-process project lock. Do not retain that lock for the lifetime of the server, an attached console, a preview, parsing, or a network request. CLI and web preserve the same busy/conflict, partial-diagnostic, intentionally-invalid-save, and manual-recovery behavior.
- Keep status, authentication, cancellation, and console controls responsive during long operations. Isolate CPU-heavy RDF work behind a bounded Node worker boundary when necessary; it runs the shared core and retains the same filesystem coordination. No additional language runtime or persistent RDF database is introduced. Do not claim responsiveness until implementation evidence demonstrates it.

### Server identity, startup, and reconnection

- One server belongs to one canonical project root. Use an exclusive runtime registration distinct from the short-lived project-operation lock to prevent concurrent starts. The record contains the project identity, an instance identifier, process identity, endpoint, running application/protocol version, and protected control credentials. It is ephemeral local state, excluded from project versioning and dependency snapshots; exact paths and encodings belong to the schema ticket.
- Restrict credentials and runtime records to the owning operating-system user, including an appropriate Windows permission mechanism. Apply the existing confinement/link checks to project-relative runtime destinations. A caller unable to establish ownership or authenticate cannot start a competing instance or control someone else's server.
- Before attaching, stopping, or reporting a server as healthy, verify the instance through an authenticated handshake matching the canonical root, instance, protocol, and process identity. A PID or reachable port alone is insufficient. A demonstrably ended owner permits guarded cleanup of its runtime registration, but not of a project transaction lock; ambiguous ownership or an unresponsive live owner produces diagnostics and explicit recovery guidance without automatic killing or duplicate startup.
- On initial startup, bind explicitly to `127.0.0.1`, obtain an available port unless `--port` is supplied, and publish readiness only after the listener and authenticated handshake work. A supplied unavailable port fails without substituting another. Reconnecting with an explicit port different from the existing server reports a conflict rather than moving or replacing it. Never accept a wildcard or remote bind address.
- Implement the server as a separate Node process from launch, with no inherited terminal dependency or visible background console window. The default foreground experience attaches a CLI console to that process; switching to the background detaches the client rather than migrating a live terminal or restarting the server. Node's detached spawn/unref APIs are documentary support, not proof that the cross-platform lifecycle works.
- Reconnection uses the server's advertised compatible control protocol and reports its actual running version. An application upgrade never silently restarts a server or changes project resources. Reject incompatible attachment with guidance to use the running version to stop it and then restart with the installed version; do not mix incompatible API/frontend releases or guess at a stop protocol. Running assets/modules must remain tied to the launched release; require stopping before an in-place package replacement that cannot preserve that release.

### Lifecycle commands and console behavior

```text
tbspec web [--port <port>] [--background]
tbspec web status
tbspec web stop
```

- `tbspec web` starts and attaches if absent, or attaches to the verified existing server. Show the actual project, version, state, and usable opening URL. Do not open the browser automatically. An interactive console streams bounded recent logs and new events and accepts an explicit `detach` action; Ctrl+C requests server shutdown. Multiple consoles may attach: detaching one leaves the others connected, while stopping the server ends all connections.
- `tbspec web --background` ensures a verified server is running, reports readiness and its opening URL, and returns without attaching. It reuses an existing instance. Unexpected terminal closure, console transport loss, or browser-tab closure leaves the server running.
- Non-TTY execution does not request input. Without `--background`, it remains an attached log/control client until interruption; EOF or a lost input stream is a disconnection, not an implicit shutdown. `--json` start/reconnect reports one readiness envelope and returns without attaching; log streams never contaminate that envelope. Document this explicitly as background-style behavior in machine-readable mode.
- `tbspec web status` never starts or attaches. Return server state, canonical project, actual application version, verified PID/instance, and URL when available. No registration means stopped; a registration that cannot be verified is unavailable/unknown, never falsely running or silently cleared. A stopped result is a successful status inspection. A live server may provide a fresh one-use opening link without changing project files or lifecycle; identify the canonical base URL separately from that transient link.
- `tbspec web stop` requests authenticated graceful shutdown without attaching; an already absent server is an idempotent success. A stop against an ambiguous/unreachable registration reports the problem and never kills a process by PID alone. Shutdown stops accepting new operations, cancels pending acquisition where safe, and allows an in-progress publication to complete or roll back through the shared transaction boundary before normal exit. If forced termination or a crash leaves pending transaction state, existing manual recovery rules apply.
- Keep runtime status distinct from project validity: a running server can serve an invalid project. Preserve CLI JSON envelopes and established exit categories; the schema ticket owns concrete status/code/field encodings. Server logs are bounded, credential-redacted operational output, not a second project revision history. Losing logs on restart is acceptable.
- This explicitly extends the functional CLI specification with background/status/stop controls and a foreground lifecycle console. Project operations retain non-interactive arguments and explicit acceptance flags; the console controls do not introduce interactive confirmations into those operations.

### Loopback authorization and browser bootstrap

- Validate the actual Host/authority against the bound loopback host and port before dispatch; do not trust proxy forwarding headers or expose permissive CORS. Authenticate every project-data endpoint, long-running operation, log/control stream, and mutation. Public static assets contain no project data or session secret.
- Generate unpredictable per-instance control credentials and tab-scoped browser session credentials. The native console authenticates with its protected local credential; browser JavaScript does not receive the server-control credential. Browser APIs require bearer headers rather than automatic cookies. Validate an Origin when present against the exact served origin; browser mutations and bootstrap exchange require that origin and reject null/foreign values. Native control requests may omit Origin only on their authenticated control boundary. Do not reject legitimate same-origin reads merely because a browser omits Origin.
- Produce a short-lived, single-use bootstrap value in an opening URL fragment. The static client removes the fragment immediately and exchanges it on the same origin for its tab-scoped credential. Do not embed a long-lived bearer in query strings, assets, logs, project configuration, or lockfiles. A used/expired link requires a fresh opening link, obtainable without console attachment via status. Restart invalidates old browser/control credentials and previews. Token/bootstrap wire formats and lifetime encodings belong to the schema ticket.
- Serve installed interface assets and fonts locally. Apply an appropriate content security policy, avoid project-supplied executable code, and prevent project labels/source text from being interpreted as HTML or script. Reads, validation, queries, and rendering never acquire remote content. Explicit dependency operations retain the approved network/source limits and original-byte staging.
- These protections enforce the loopback/browser boundary; they do not promise isolation from an adversarial process already running as the same operating-system user.

### Revision-bound previews and cancellation

- The shared core prepares an operation plan containing its precise read set and destination revisions, affected files, proposed bytes, and required acceptance/impact. For web acquisition, stage the exact fetched closure outside the consumer lock and retain it in a private preview workspace. Return an opaque server-instance/session-bound handle and its reviewed impact; the browser never submits a free-form replacement write plan.
- Apply that handle with explicit acceptance, reacquire the project-operation lock, and verify every relevant file/inventory revision before publishing the same staged bytes. Do not reacquire from upstream, silently replan, or substitute a newer plan. Mismatch returns a conflict and requires a new preview. Console detach does not invalidate browser sessions or previews. A preview is consumed on successful application and invalidated on cancel, relevant change, restart, or disclosed bounded expiry; it cannot be reused for a second commit.
- Bind preview ownership to the requesting browser session; do not let another tab silently inherit or accept it. Reconnection of a terminal does not transfer browser drafts. Closing a tab may leave an unused preview until expiry; restarting does not restore drafts or preview handles from disk.
- Across CLI invocations preserve the dependency contract's reacquire-and-regenerate rule. A later apply must still evaluate and explicitly accept the newly computed impact and never treat an old terminal display as acceptance of different bytes. Exact representation of an accepted preview fingerprint and any additional CLI binding argument are owned by the concrete schema decision, without weakening the approved revision/acceptance guarantees.
- Cancellation before publication discards only that operation's staged state. Once publication has begun, use the transaction's completion/guarded-rollback rules, not an unsafe interrupt between file replacements. On an uncertain transport outcome, do not automatically retry a write or claim it failed; inspect current revisions and diagnostics before planning another request.

### Distribution, bundles, and compatibility

- Publish one npm package with a Node executable entry point, compiled CLI/core/server modules, prebuilt static web assets, and the immutable starter release inventory, RDF/SHACL/design files, parser contexts, digests, and source/license attribution. Installed runtime operations do not require TypeScript, Vite, a build tool, Java, Python, or .NET. Git remains optional and is required only for explicit Git acquisition.
- Resolve bundled paths relative to the installed module, never the user's working directory. Do not execute project-local package scripts/plugins or load a project-controlled web bundle. Pin application dependencies through the release lockfile and verify the actual packed artifact contains everything required for offline use.
- `init` copies the selected packaged starter release into the project and records it through the existing snapshot/lock contract. Package upgrades do not rewrite a manifest, update snapshots, change model types, or migrate schemas implicitly. Starter updates use the existing explicit dependency preview/impact flow; resetting a type uses its already locked version. A requested bundled version absent from the installed release must fail actionably rather than substitute another version.
- Keep package/runtime protocol versions distinct from project-file and JSON schema versions. Concrete compatibility rules, runtime/status encodings, preview fingerprints, and transient credential treatment belong to [Define concrete project file and machine-output schemas](14-concrete-file-and-output-schemas.md).

### Required implementation evidence and scope

Require focused checks on Windows, macOS, and Linux showing: installation of the packed npm artifact with Node 24; offline startup/init/render/query/validation; fixed-root confinement; two concurrent starts producing one verified instance; independent projects; explicit port conflicts; foreground and detached launch without extra windows; detach/reconnect without losing browser sessions; unexpected terminal closure preserving the server; status without starting or attaching; stopped/unresponsive/stale/mismatched process states; authenticated graceful/idempotent stop; multiple-console detach versus shared stop; bounded redacted logs; non-TTY and single-envelope JSON behavior; version mismatch refusal; exact Host/Origin/token/bootstrap rejection and replay/expiry handling; no private data in public assets; CLI/web operation parity; responsive controls during acquisition/RDF work; revision-bound preview application without refetch; preview ownership, invalidation, and consumption; no unsafe cancellation/retry during commits; unchanged locked resources after package upgrades; and the already-approved recovery/conflict behavior. These are future acceptance requirements, not tests already run.

No new glossary term is needed: server, console, token, and preview here are implementation/interface concepts, not additions to the domain language. No ADR is required for the replaceable server/client/packaging mechanism; the lasting shared-runtime trade-off already lives in ADR 0004. The functional specification records the approved CLI lifecycle and security extensions and links this decision. No additional in-scope question currently requires a new child ticket; concrete schemas, layout, and specialized forms remain in their existing tickets. Production code, publication, and deployment remain outside this map.
