# Choose safe project file mutations and edit conflicts

Type: grilling
Status: ready-for-human
State: resolved
Assigned to: Codex
Blocked by: 05

## Question

How should shared project operations stage and commit changes to RDF files, `tbspec.toml`, `tbspec.lock`, and snapshots so recoverable failures leave prior state available? Decide a minimal cross-platform conflict check for CLI and loopback web edits, including the web stale-save rule, path confinement under the selected project root, preservation of unrelated TOML keys/comments, and honest crash-recovery limits. Do not add a persistent RDF database by default.

## Comments

- The user accepted staged multi-file writes with restoration of prior files after recoverable errors. Other programs may observe intermediate files during installation; `tbspec` coordinates its own reads and writes.
- After an interrupted operation, the user chose to block further writes and guide manual recovery from retained originals rather than restore automatically.
- The user chose conflict checks on the operation's read inputs and destinations, not every project file. A web save based on a stale disk version is rejected and requires a reload.
- The user accepted best-effort protection against concurrent local processes: reject escaping paths and recheck immediately before writes, without claiming safety against an adversarial process that swaps paths or files during that final window.
- The first interview round proposed immediate project-busy conflicts, manual recovery after incomplete rollback or interruption, revision-bound resolution of stale web saves, and rejection of internal write links.
- The user invoked `auto-grill` to complete discovery autonomously. The full proposal included coherent tool reads, SHA-256 revision checks, staged multi-file changes, guarded rollback, surgical TOML edits, path confinement, and explicit local-filesystem and crash-recovery limits.
- The user explicitly approved the complete contract below with "de acuerdo". This resolves the architecture decision; production implementation remains outside this map.

## Answer

### Existing constraints

The [functional specification](../../mvp/spec.md#file-and-state-contract) makes RDF/TOML files canonical, requires preservation of unrelated manifest keys and comments, rejects stale web saves, and requires prior state to remain available on recoverable multi-file failures. It permits manual or Git recovery after a crash. [Choose the RDF-to-canvas projection and editing boundary](07-rdf-canvas-projection.md) additionally permits saving invalid Turtle and requires explicit resolution of drafts made stale by canvas edits. [ADR 0003](../../../docs/adr/0003-allow-confirmed-breaking-removal.md) permits confirmed changes that break references and excludes a second revision-history system.

### Coordination and conflict checks

- Use one short-lived, cross-process project lock shared by CLI and loopback web operations. Acquire it with exclusive file creation under the canonical project root; the coordination file is distinct from the versioned dependency lockfile `tbspec.lock`. A competing operation returns a project-busy conflict immediately. Different projects remain independent.
- File reads used to assemble an operation's input snapshot also take this lock. Read the required files and relevant directory inventories together, then release it for parsing, queries, validation, rendering, and explicit dependency acquisition. Commit reacquires the lock and checks that the input snapshot still applies. Do not hold it while awaiting network requests or user decisions. Tool readers cannot observe an intermediate tool commit; external editors do not participate in the protocol.
- Compare SHA-256 of exact file bytes, with an explicit absent-file state for new destinations. Include affected files, configuration, lock records, and any other files or directory inventories used to determine impact or the write plan. Do not rely on modification timestamps, byte length, or file watchers. A newly added view or reference that changes a project-wide plan invalidates that plan.
- Capture expected revisions with web loads and CLI previews. Recheck them under the lock before publishing, and recheck each affected path immediately before its filesystem action. A mismatch aborts the whole operation rather than silently replanning an already accepted impact. A stale preview must be regenerated and accepted again where confirmation is required.
- Keep the web draft on conflict, show the current disk version, and let the user prepare a new save against that version. Explicit replacement is a new request bound to the reviewed current revision; it never bypasses the revision check. Repeated external changes produce another conflict. Track the canvas/source draft revision separately; its existing explicit-confirmation rule still applies.
- Immediately after exclusive creation, write and close an ownership record in the coordination file before staging or changing live paths. Record a unique acquisition token, host and boot identity, process ID, and process start identity so PID reuse cannot identify another process as the owner. On startup or lock contention, validate the record against the operating system: a matching live process means the project is busy; a verifiably ended owner means the lock is abandoned. Missing, partial, malformed, foreign-host, or otherwise unverifiable ownership is unknown, including a crash between file creation and completion of the record. If the platform cannot verify the full process identity, use unknown. Abandoned and unknown locks block normal project operations and require manual recovery even when no transaction record exists. Never remove a lock automatically based on age or a PID alone. A normal release removes only the lock whose acquisition token still matches the holder's record.

### Staging, publication, and recovery

- CLI and web call the same project-operation boundary. A plan identifies every created, replaced, moved, or deleted file, its expected prior revision, and its proposed bytes. This includes RDF, manifest settings, saved queries and parameters, dependency lock records, and managed snapshot files when the operation owns those changes.
- Prepare all new bytes and exact before-images in a private, temporary transaction workspace under `.tbspec/`, on the same local filesystem as the affected files. Record the affected relative paths, prior absence or content, proposed signatures, and publication progress. Finish preparation before changing canonical files. Stage snapshot acquisitions completely before changing their current files or lock record.
- Publish staged files with native same-filesystem replacement operations rather than truncating live files. Check creation and move collisions; never intentionally replace an unrelated destination. Handle snapshot changes as part of the same plan. Enumerate managed files explicitly; do not recursively delete an unverified directory. Preserve existing file permissions and restrict temporary copies containing project data.
- On normal success, every planned file and the matching lock records are current. Mark the transaction complete before treating cleanup as a separate task. Cleanup failure after completion reports success with a warning and the retained workspace; it must not claim that the operation failed or silently roll back a completed change. Retain no ongoing undo history after cleanup.
- On a handled failure before completion, restore applied changes in reverse order and retain the original error. Restore a path only when it still matches the transaction's expected post-change state; do not overwrite an intervening external edit. Remove transaction-created files only on the same condition. Earlier files and lock records remain available in before-images until restoration is verified.
- If rollback cannot finish, or a process exits with a pending transaction, preserve its workspace and block normal project operations. Allow recovery diagnostics and read-only inspection of the files, clearly describing that the project may contain mixed state. Manual recovery or Git restores a coherent state; only then may the abandoned transaction and lock be cleared. Do not automatically replay or discard pending transactions.
- Recovery inspection reports available ownership details, affected paths, and the recovery location; explicitly report missing or incomplete metadata rather than assume live files are unchanged. Before manual recovery, stop all CLI and web processes that can access the project and prevent new invocations. Preserve the coordination file and available transaction records and originals, inspect the project, then restore or explicitly accept its on-disk state before clearing retained lock and transaction state. If exclusive access cannot be established, leave the lock in place.

### Path and editing boundaries

- Resolve the selected project root to its real directory once. Treat resource paths as project-relative selectors, separate from RDF IRIs and external dependency source locators. Reject absolute/drive/UNC paths, traversal outside that root, Windows alternate-data-stream paths, and invalid or reserved path components. Validate dependency IDs and other generated path segments before joining them.
- Reject writes through internal symbolic links or Windows junctions, including the target, existing parent directories, coordination files, and temporary workspace. The selected root itself may be reached through a link after canonicalization. Check both lexical containment and the actual existing ancestors; recheck them before mutation. Reject overlapping or platform-equivalent destinations and multiply linked writable files rather than assuming canonical path strings uniquely identify files.
- Generic editing changes project-owned resources only. Locked snapshots are read-only to editors; explicit dependency administration may replace or remove managed snapshots and their lock records through the shared transaction boundary. Dependency acquisition may read external sources, but every project destination remains confined.
- Edit human-authored TOML through parsed syntax with source ranges or a concrete syntax tree. Change only the requested setting; preserve unrelated bytes, keys, comments, and line endings. Reparse the result and check the intended semantic change before staging it. Malformed TOML or an unsupported surgical edit fails without rewriting the whole document. The tool-written `tbspec.lock` may be serialized as a whole. Exact fields and parser package selection remain for the schema decision and implementation respectively; a comment-preservation check must precede adopting the editor.
- Raw source saves may contain invalid RDF and retain the submitted source text, with diagnostics. Graph operations must parse every graph they actually rewrite and preserve unknown RDF statements, languages, and datatypes; Turtle formatting/comments need not survive those rewrites. Do not require unrelated graphs to pass SHACL before a save. Project-wide refactoring must refuse when a required graph cannot be parsed safely.
- Successful, explicitly accepted removals or updates may leave the project semantically invalid. Report that state; do not reinterpret it as an I/O failure or roll back an intentional change. Preserve existing impact and confirmation requirements.

### Approved assumptions and limits

- Target an ordinary local project directory on one filesystem. Network shares, filesystem aliases exposing the same project through independent mount paths, and unsupported filesystem semantics are outside the guaranteed coordination contract. Node documents that [exclusive creation can fail to provide its intended guarantee on network filesystems](https://nodejs.org/docs/latest-v24.x/api/fs.html#file-system-flags).
- The lock serializes cooperating tbspec processes. Content checks catch observed external changes, including comment-only changes, but cannot make external editors participate in the transaction. External readers can observe partial multi-file publication; an external writer can race a check and a later replacement. Concurrent hostile local filesystem mutation is outside this process-level boundary. Node explicitly documents [check/use races](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsaccesspath-mode-callback) and notes that [canonical pathnames are not unique](https://nodejs.org/docs/latest-v24.x/api/fs.html#fspromisesrealpathpath-options). Rejecting links and rechecking ancestors protects supported writes without promising an OS sandbox.
- A process crash or power loss can leave mixed state or incomplete temporary copies. Staging and before-images improve recovery but provide no multi-file crash atomicity or power-loss durability guarantee. Windows sharing/permission errors and cross-filesystem operations must fail safely; no retry may weaken conflict checks.
- These assumptions are reversible by changing the coordination/recovery implementation later without changing RDF resource identities. Rejecting internal write links restricts project layout; immediate busy errors restrict concurrent throughput. Add stronger coordination or recovery only when required.

### Acceptance evidence to require during implementation

Use a small runnable check over temporary project files, with failure injection between publication steps. It must demonstrate: successful multi-file publication; byte-for-byte rollback of replaced/deleted/moved files and lock records; no canonical changes on staging failure; conflicts between independent CLI/web processes; blocked normal operations after interruption before ownership metadata is complete, PID reuse, or unverifiable ownership; rejection of stale and comment-only revisions; absent-destination and changed-inventory conflicts; draft retention and a second conflict after attempted resolution; confinement for traversal, links/junctions, and aliased targets; unrelated TOML byte preservation; allowed invalid-Turtle saves and confirmed semantic invalidation; preservation of external edits during attempted rollback; retained recovery files and blocked normal operations after incomplete rollback or interruption; and success-with-warning after completed-transaction cleanup failure. Validate platform-sensitive filesystem behavior on Windows, macOS, and Linux before claiming all three supported. No production code or prototype is introduced by this decision ticket.

### Scope and downstream decisions

No persistent RDF database, automatic merge, filesystem watcher as a correctness mechanism, automatic crash replay, distributed locking, new recovery CLI command, or internal revision history. Exact TOML/output schemas remain in [Define concrete project file and machine-output schemas](14-concrete-file-and-output-schemas.md); dependency acquisition mechanics remain in [Choose dependency snapshot and resolution mechanics](12-dependency-resolution-architecture.md); packaging and route/session-token integration remain in [Choose the shared CLI and loopback web architecture](13-cli-web-runtime-boundary.md).

No new domain term has emerged: file revisions, locks, and transactions are implementation concepts and do not belong in the domain glossary. No separate ADR is needed: the coordination and recovery choices can change without altering resource identities, and their trade-offs are recorded here. This resolution introduces no production implementation or additional decision ticket.
