# Choose dependency snapshot and resolution mechanics

Type: grilling
Status: ready-for-human
State: resolved
Assigned to: Codex
Blocked by: 05, 10

## Question

How should the MVP discover one selected resource and its allowed closure from directories, Git, and single-graph HTTP(S) URLs; snapshot and hash every included file; and resolve ontology and visual-design precedence without merging losing snapshots? Define the smallest cross-platform source acquisition and lockfile boundary consistent with ADR 0001 and spec 0.1, including offline validation and drift checks. Distinguish source fetches triggered by explicit dependency actions from local query or validation.

## Answer

Use the approved dependency acquisition and resolution contract below. It resolves only **Choose dependency snapshot and resolution mechanics** and specifies future implementation behavior; it does not claim that source adapters, parser integration, or cross-platform checks have been implemented or executed.

### Existing evidence and constraints

- Preserve [functional spec 0.1](../../mvp/spec.md), [ADR 0001](../../../docs/adr/0001-lock-external-resources.md), the [runtime baseline](05-select-rdf-stack.md), the [query boundary](08-query-dataset-boundary.md), the [validation boundary](09-shacl-validation-boundary.md), the [transaction boundary](10-file-transaction-boundary.md), and the [starter contracts](11-starter-resource-contract.md).
- The spec already fixes project-unique dependency IDs, one selected ontology/model/design per add, original local snapshots under `.tbspec/dependencies/<id>/`, a versioned TOML lockfile, SHA-256 for each included file, explicit updates, source ontology bindings for locked models, ontology/design precedence, and no implicit network acquisition during ordinary project operations.
- Directory and Git inventories may reveal declared closure and directly associated SHACL, designs, and source design choices. A standalone resource URL identifies one graph, is not recursively crawled, and may retain unresolved references with diagnostics. Upstream views, presentations, unrelated models, saved queries, and whole source manifests are not automatically imported.
- The earlier Node research established strict Turtle/N-Triples parsing and warned that broad format dispatch can enable remote context loading. The approved P-Plan starter additionally needs its pinned RDF/XML source interpreted locally. Acquisition research is recorded in [the supporting note](../research/dependency-acquisition-contract.md); its documentary findings are not a runtime proof.

### Acquisition boundary

- Use three small source adapters: directory, Git, and HTTP(S). Each produces an inventory of original bytes and normalized interpretation metadata; it does not mutate the consuming project. Shared discovery, closure traversal, resolution, and publication sit above the adapters and are reused by CLI and web.
- **Installed-Git boundary:** require installed Git only when a user explicitly accesses a Git source. Directory, HTTP(S), bundled starters, queries, validation, rendering, and already locked Git dependencies do not require Git. Report missing Git without changing the project. Do not bundle a second Git implementation or add another language runtime.
- A directory source is an explicitly selected root, with a source-relative resource selector. Canonicalize the root and confine discovery to it. Inspect supported RDF files and source metadata, excluding unrelated `.git` and temporary directories. Read managed dependency files only through the relevant source lock inventory. Never follow internal links/junctions, absolute manifest paths, or traversal outside the source root; an explicitly selected root may itself be reached through a link after canonicalization.
- If the selected directory is a tbspec project, take its existing project read lock to capture the relevant manifest, lock entries, resource bytes, and directory inventory together. Release it before parsing or consumer publication. Never hold the consuming project's lock while acquiring a source, and never hold two project locks at once. For an ordinary directory without a cooperating lock, recheck included files and relevant discovery metadata after copying; reject an observed concurrent change. This is a best-effort local read boundary, not protection against hostile writers or a guarantee of a point-in-time source snapshot.
- For Git, resolve the requested ref, or the remote's default HEAD when omitted, once to a commit and read files from that immutable tree in a private temporary bare repository. Record both the requested revision policy and resolved commit. Fetch with automatic tags and submodule recursion disabled; force `core.hooksPath` to an app-owned empty directory on every command, since a bare fetch can still trigger reference-transaction hooks. Read raw tree/blob objects without filters. Do not check out files, run repository hooks or filters, initialize submodules, or automatically fetch LFS content. A required LFS pointer or submodule-only resource is unsupported and fails with an actionable diagnostic. An explicit commit stays pinned; branches/tags/default HEAD are resolved again only by explicit inspect/check/update actions. If a server cannot serve the requested pinned commit, fail rather than substitute a branch tip.
- Invoke Git with argument arrays and no shell. Permit HTTPS/SSH repository locators and explicitly selected local repositories; reject option-like locators, arbitrary remote-helper protocols, `ext`, and insecure Git/HTTP transports. Do not inherit configuration from the source repository. Installed Git, the user's deliberately configured authentication providers, and the local account remain trusted; do not claim that invoking Git is an OS sandbox. Apply bounded execution and terminate child acquisition on cancellation.
- HTTP(S) retrieves exactly the requested RDF graph, with bounded redirects, time, and response size. Do not fetch HTML-linked resources, guessed sibling files, RDF term IRIs, `owl:imports` targets, JSON-LD contexts, or XML entities. A resource locator is permission for that explicit source action, not for later parser or validation requests. Permit local/private HTTP endpoints when explicitly chosen; this local tool is not a public URL-fetching service.
- Persist credential-free source locators only. Use transient credentials or trusted external authentication; redact errors and redirects. Do not store userinfo, authorization headers, secret query parameters, or credential-bearing Git locators in manifests, lock records, or logs. If a source cannot be represented by a stable credential-free locator, reject it with guidance rather than silently persist or reuse a broken redacted URL. No new credential provisioning workflow is introduced.

### Resource discovery and closure

- `inspect` lists the source's discovered resource inventory and associated support, reporting malformed entries without importing them. A direct HTTP(S) graph has no discoverable inventory; adding it still works. An explicit relative selector is required when a directory/Git source has multiple selectable primary resources. Do not guess a winner by filename order.
- For a tbspec source, follow only declared interpretation edges: the selected model's recorded ontology binding, an ontology's declared imports when mapped to available recorded resources, concrete-model schema references, associated SHACL, associated visual designs, and the source's relevant winning design choices. A selected design also brings discoverable declared vocabulary associations needed to interpret its rule targets. RDF predicate/object references and namespace prefixes alone are not acquisition instructions.
- Reuse the source project's already locked dependency files and recorded associations rather than refetching their original sources. Preserve their original provenance and resolved commits. A Git source must contain every required snapshot file at the selected commit; absent uncommitted source snapshots do not authorize fetching their lockfile URLs. Copy only the selected resource's reachable interpretation closure and associated support. A source configuration change unrelated to that closure is excluded.
- Traverse with a visited set keyed by source resource identity, preserve dependency edges, and handle cycles without infinite recursion. Retain distinct versions reached by different paths; do not collapse them solely because their ontology IRIs match. Compute dependency distance from direct consuming-project additions using shortest paths. A cycle does not create a nearer candidate.
- Capture source model-type bindings and inherited choices as snapshot metadata. Keep RDF bytes unchanged, including models' type-name statements. A same-named model type in the consuming manifest never silently rebinds a locked model. References to bundled defaults from a source project use that source project's locked release, not the current application's default release.
- **Incomplete-source policy:** if an included file or explicit file association exists in the declared closure but is missing, unreadable, corrupt against its source lock signature, unsupported, or unparsable, reject acquisition before publication. Also reject ambiguous managed roots, contradictory kind overrides, or unusable metadata needed to establish the selected binding. Do not reject an unrelated malformed source resource.
- A resource with parseable bytes may still have semantic violations or unresolved IRI references. Report these through ordinary diagnostics; do not invent a location or fetch to repair them. An unmapped import/schema IRI is unresolved metadata, not a declared file that can be copied. For a bare URL, missing discoverable ontology/support associations are the already-agreed unresolved-reference case. This distinction avoids claiming complete validation while preserving the specified standalone-URL workflow.
- No implicit SHACL import expansion or executable extension loading. Constraints requiring absent support are explicitly skipped/partial under the existing validation contract. Source view/presentation pairs and their positions are not part of dependency closure; views of a locked source remain project-owned.

### Parsing, bytes, and signatures

- Preserve and hash each included file's exact bytes; do not normalize Turtle, line endings, blank-node labels, or XML before snapshotting. Record the chosen media type and original effective base IRI as interpretation metadata so moving a snapshot cannot change relative IRI resolution. Include that metadata in interpretation comparisons. Scope blank nodes to their source graph.
- Enable an explicit single-graph parser allowlist: strict Turtle, strict N-Triples, and locally parsed RDF/XML required by the pinned P-Plan source. Use direct `rdfxml-streaming-parser@3.3.0` alongside the already pinned N3 stack, with application lockfile transitives pinned; the supporting research establishes the documented API/interface fit, not executed integration or entity safety. Do not replace the existing query/validation engines or enable a general network-capable parser registry.
- For HTTP, a recognized supported Content-Type determines format; use a supported filename suffix only when the MIME type is absent/generic. Unsupported or conflicting data fails parsing rather than falling through a permissive parser. For files, explicit supported suffixes select the parser. Reject remote-context formats and dataset serializations such as TriG/N-Quads. Confirm that every emitted quad is in the default graph before assigning the recorded graph identity.
- **Conservative RDF/XML profile:** reject DOCTYPE/entity declarations in arbitrary input before RDF parsing, with XML-aware handling of declarations/encoding rather than a raw substring safety claim. The pinned P-Plan file actually contains fixed internal namespace entities; allow those original bytes only when their SHA-256 matches a vetted bundled release inventory entry. Its namespace values are literals, not external fetches. Modified/new DTD-bearing sources are unsupported until explicitly vetted or a broader safe parser profile is implemented. Never permit external SYSTEM/PUBLIC entity resolution. Preserve the original vetted bytes rather than silently rewriting the ontology. This reversible restriction and the parser's no-network/entity behavior require implementation checks before any general RDF/XML support claim.
- Hash files individually with SHA-256. A graph-content signature uses that graph's byte digest and parser context; use it for ontology-content equality. Separately compute an aggregate interpretation signature from an unambiguous, deterministic encoding of included file roles/identities, byte digests, parser contexts, dependency edges, source bindings, support associations, kind overrides, and retained relevant design choices; use this broader signature for drift. Exact TOML field names and canonical encoding belong to [Define concrete project file and machine-output schemas](14-concrete-file-and-output-schemas.md).
- Transport provenance (for example an unrelated newer Git commit) is recorded separately from interpretation content. A formatting-only change in an included RDF file counts as changed; semantic RDF canonicalization is excluded. Equal graph bytes with different effective bases are not silently treated as the same interpreted graph. Different support/design associations do change the aggregate interpretation signature, but do not by themselves turn identical ontology content into an ontology-version conflict.
- Verify the needed snapshot files against their locked hashes before using them. A missing or modified locked file is a local integrity error, not permission to repair it from its source. Queries, validation, status, and rendering continue to use only local bytes.

### Stored candidates and effective resolution

- Store each explicitly added dependency and its captured closure independently. Duplicated closure bytes are acceptable in the MVP; updating/removing one addition must not mutate another addition's retained files. Avoid a shared content store, hidden transitive upgrades, or cross-snapshot garbage collection.
- Resolve ontology candidates by ontology IRI, not filename, `owl:versionIRI` ordering, or semantic version guessing. Preserve the existing rank: consuming-project explicit choice, project-owned ontology, direct dependency, nearest transitive dependency. Identical graph-content signatures form one effective ontology candidate; retain their provenance and distinct recorded support contexts. Different graph-content candidates tied at the winning rank/distance remain a conflict and are not merged. Resolve visual choices through their separate rules below. Deduplicate equal shapes; multiple distinct explicitly associated shapes for an identical ontology remain separate validation runs, rather than changing the ontology's content identity. Never take support from a different-content losing ontology to enlarge the winner's constraints.
- **Approved query-contract amendment:** register one winning ontology and its effective support/associations for full-project query assembly; retain losing files in the locked inventory. This explicitly refines the earlier query ticket's literal instruction to load every locked graph and the spec's all-resources named-graph wording, because two retained ontology versions cannot both occupy the same named graph without a forbidden merge. The query ticket and spec record this approved amendment and link this decision; their earlier all-locked-graph wording did not already satisfy it. Preserve original RDF graph IRIs and do not invent aliases for losing ontologies. The duplicate-IRI guard still rejects genuine collisions after ontology resolution, including unrelated model/support collisions. The schema ticket must specify a stable root-ID-plus-file selector for inspecting a retained nested file; isolated inspection/query keeps its original graph IRI. Full validation still reports syntax/integrity problems in retained files and validates each locked model in its own recorded source context, without adding losing vocabulary to other targets.
- Model, visual-design, or support graphs with the same graph IRI and divergent contents have no ontology-version precedence rule. Report an identity collision; do not use ontology precedence to hide it. Equal byte/interpretation copies may share one effective graph while keeping associations/provenance; a real collision cannot be repaired by merging definitions.
- `dependency select <ontology-iri> <id>` identifies the matching candidate supplied by that dependency's recorded inventory. If one ID contains multiple different versions without a recorded source winner, fail as ambiguous instead of choosing the first. Show candidate provenance and paths. The user can add the desired resource as its own explicit dependency and select that ID; no new CLI flag or silent internal ID scheme is introduced. Exact nested graph/support selectors remain the schema ticket's responsibility.
- Resolve whole visual designs per exact target concept using the existing rank: consuming-project choice, project-owned design, design associated with the effective selected ontology (including its relevant source choice), then other inherited designs ordered by distance. Same-rank/distance ties are errors. Ignore an inherited choice outside its source context or whose design is unavailable; report a broken choice rather than silently falling back. A consuming-project choice may override inherited choices. Do not merge appearance fields, inherit rules through class/property hierarchies, or let per-view `chosenRule` choose a losing design.
- Keep supports associated with the resource/snapshot that supplied them. Selecting a different ontology changes the consuming project's effective support/design context; shapes from a different-content losing candidate do not become constraints on the winning ontology merely because the ontology IRI is equal. Validate a locked external model using its recorded source ontology bindings, source resolution choices, and associated support; do not rebind it through the consuming manifest or consumer-wide winner. Project-owned models use consuming-project resolution. Both cases retain the one-target-data-graph validation boundary. A source binding that cannot be satisfied is diagnostic. Source snapshots remain available to their original dependent resources even when their ontology loses in the consuming project's query registry.

### Check, update, support, and removal

- **Drift policy:** reacquire the selected source/closure for `check` and compare its interpretation signature. Included byte changes, added/removed included files, changed declared bindings/support, changed effective parser bases, or changed relevant source design choices mean `changed`. An unrelated source-project file, unrelated manifest key, or newer Git commit with identical interpretation means `unchanged`. Report the observed commit separately without changing the stored commit or snapshot.
- An absent/unreadable source or inability to obtain required bytes means `unavailable`, with a reason; do not pretend it is an unchanged source. If retrieved included bytes differ but the new RDF/metadata is malformed, report `changed` plus the parse diagnostic and incomplete closure comparison; an unusable replacement cannot be applied. Local snapshot corruption is a separate diagnostic. `check` never changes canonical files. For multiple IDs, report each result; I/O/unavailable failure takes exit `4` precedence over drift exit `1`, otherwise clean checks exit `0`, following the spec's categories.
- `update` previews by default. Acquire once, stage exact proposed bytes/metadata, resolve candidates, and run downstream diagnostics against an in-memory proposed project state. Explain source changes, winner changes, affected files, invalid/skipped checks, broken choices, and existing baseline problems separately. Compare against the captured current state: `--apply --accept-impact` is required for newly introduced or worsened invalidity, including new resolution ties or unavailable validation prerequisites. Unchanged baseline errors alone do not trigger that extra gate or require unrelated repairs. If new impact cannot be assessed because a required affected resource is invalid, report that uncertainty and require explicit impact acceptance; acquisition/parse/I/O failure still cannot be bypassed.
- Use the [normative diagnostic identity and impact comparison](../contracts/file-and-output-schemas.md#diagnostic-identity-and-impact-comparison), including full warning/info baselines, per-condition severity/multiplicity, and check coverage. New errors cannot be offset by resolved errors; anonymous terms from changed source graphs cannot silently match by label. Blocked affected required checks remain unassessable even when their baseline blocker is unchanged; unrelated baseline failures do not add an acceptance gate. This shared rule also normalizes identities and preserves multiplicity in preview fingerprints.
- A preview must bind application to its exact acquired bytes and expected consumer revisions. Do not refetch during application and silently install different content. Across CLI invocations, reacquire and regenerate the preview; if it differs, require a new review/acceptance. How CLI/web carry a revision-bound preview is an interface detail for [the shared runtime ticket](13-cli-web-runtime-boundary.md); it must preserve the transaction ticket's existing guarantee.
- Added/support-associated resources use the same staging and interpretation machinery. Physical acquisition failures prevent publication. A parseable addition that introduces semantic/resolution conflicts may be retained with diagnostics under the spec's exit/status semantics; there is no unlisted `dependency add --accept-impact` flag. Updates keep their specified stronger impact gate.
- Manual `support set` is for associations absent from the source, as specified. It snapshots the selected SHACL/design and its discoverable required interpretation closure, records explicit attachment provenance, and leaves all original RDF unchanged. Updating the main dependency preserves manual attachments while refreshing discoverable source support. If the source later supplies the same role, keep both attachments: deduplicate equal SHACL graphs and run distinct associated SHACL graphs separately; keep all designs as candidates subject to the existing explicit-choice/precedence/tie rules, without treating a manual attachment itself as a winning design choice. Preview the changed active support set and its impact. Checking the dependency also checks its manually attached source resources. Clearing one association changes only that association; retain detached files/records until explicit removal of their owner. Detached supports are not active constraints, and unrelated updates never silently reacquire them.
- Rename updates consumer-owned references, the lock inventory, and its managed directory through the shared transaction; preserve RDF IRIs, original bytes, source metadata, and content identities. Removal requires existing impact inspection and confirmation. It removes only the selected dependency's managed files and records; other independent dependency snapshots and project-owned views remain, potentially with broken references. Never implement a silent cascade.
- Stage acquisition outside the consumer lock, then publish the complete plan using the approved SHA-256 revision checks, short-lived lock, before-images, guarded rollback, and manual recovery contract. Normal success installs files and matching lock metadata together; handled failures preserve previous state. This does not promise multi-file crash atomicity. A source disappearing after capture does not invalidate a complete staged snapshot.

### Bundle bootstrap and operational limits

- Ship immutable starter RDF, shapes, designs, and required standard vocabularies with an explicit release inventory, source/license attribution, original parser contexts, and digests. Copy the selected release's original files into the project during `init`; no network is needed. P-Plan remains the approved pinned version 1.3, independently of current upstream content. A tool upgrade never changes existing locked bytes or choices. A bundled-source update is explicit and participates in the same preview/impact process.
- **Conservative, reversible limits:** default acquisition limits of 64 MiB decoded bytes per graph, 256 MiB total included bytes, 1,000 included files, five HTTP redirects, and a five-minute overall acquisition deadline. Enforce limits during streams/traversal, not after complete materialization. Monitor Git's temporary workspace against a 1 GiB budget and terminate acquisition on excess; this is a best-effort process limit rather than an exact filesystem quota, and included-file limits do not bound a repository's transfer. Implementation must demonstrate cancellation and reporting. Exceeding a limit fails acquisition with its reason, leaves current state intact, and requires an explicit configured higher limit for larger sources. Exact configuration fields belong to the schema ticket.
- Emit diagnostic categories for source availability/acquisition, unsupported format/source feature, incomplete declared files, local integrity, unresolved associations, ambiguity/resolution, drift, and commit conflicts, preserving the existing exit/JSON conventions. Concrete stable codes and fields remain for the schema ticket. Do not write persistent source credentials, a second revision history, or an automatic retry that weakens accepted revision checks.
- No cross-platform execution has been performed for this decision. During implementation require checks on Windows, macOS, and Linux for directory copying, argument/transport handling, immutable Git reads, cancellation, and the existing transaction boundary.

### Required implementation evidence

Require focused fixtures demonstrating: only the selected resource/closure/support is retained; source snapshots are reused offline; unrelated malformed resources are excluded; cycles terminate; locked external models keep source bindings; raw bytes and bases survive relocation; RDF/XML P-Plan parses with no entity/network loading; unsupported datasets/formats fail; an incomplete required file leaves an existing snapshot untouched; a bare URL retains unresolved references diagnostically; source/credential/redirect/path limits apply; Git hooks, filters, LFS, and submodules are not executed; a missing Git executable affects only Git acquisition; inherited ontology/design ties and explicit winners work without triple/property merges; retained losing ontology inspection and genuine post-resolution duplicate errors both work; irrelevant commits/config changes are unchanged while included bytes/support/choices drift; manual attachments survive main-source updates and support clearing retains files; local corruption is detected without a fetch; stale previews are rejected; cancellation and failed multi-file publication preserve prior state; pinned bundle initialization and all ordinary query/validation/rendering remain offline. These are future acceptance requirements, not tests already written or passed.
