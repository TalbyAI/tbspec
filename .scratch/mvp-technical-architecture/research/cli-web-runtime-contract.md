# CLI and loopback web runtime contract: research findings

Research date: 2026-10-03. This note records current documentary facts for [issue 13](../issues/13-cli-web-runtime-boundary.md); it does not choose an interaction/lifecycle option or claim integration has been implemented or tested.

## Runtime and server shape

As of this research date, Node 24 is listed as LTS, with 24.21.0 the latest LTS release. An npm package can expose a command through `package.json` `bin`; npm links it into PATH and creates a Windows `.cmd` shim, and the executable should use a Node shebang. This package form therefore expects Node to exist on PATH; it is not by itself a standalone executable. [Node releases](https://nodejs.org/en/about/previous-releases) · [npm `package.json` bin/files](https://docs.npmjs.com/files/package.json/)

TypeScript compilation erases types and emits ordinary JavaScript, which Node can run; it adds no TypeScript runtime. Vite's production build emits static assets intended for static hosting (by default under `dist`). Node's stable `node:http` module provides a low-level request listener/server, so a Node process can serve those files and same-origin API routes from one listener. The resulting static-SPA arrangement needs HTTP routing, static-file handling, and an SPA fallback in application/server code, but no React SSR renderer in production. [TypeScript handbook](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html) · [Vite production build](https://vite.dev/guide/build) · [Node 24 HTTP API](https://nodejs.org/download/release/v24.21.0/docs/api/http.html)

TanStack Start is a full-stack framework with client/server builds, server routes, server functions, middleware, and full-document SSR; its docs describe SSR as the default. A Start request handler routes server requests through those features, and the server entry point handles SSR, server routes, and server-function requests. Start also offers SPA mode to disable server-side route loading/rendering. If Start server routes/functions remain in use, a Start server handler/build remains part of the runtime even when SSR is disabled. The official Start landing page currently labels the release “RC”; that label should be rechecked at any later selection date. [Start overview](https://tanstack.com/start/latest/docs/framework/react/overview) · [server routes](https://tanstack.com/start/latest/docs/framework/react/guide/server-routes) · [server entry point](https://tanstack.com/start/latest/docs/framework/react/guide/server-entry-point) · [selective SSR](https://tanstack.com/start/latest/docs/framework/react/guide/selective-ssr) · [Start landing page](https://tanstack.com/start/latest)

Either arrangement can call shared project operations outside transport handlers: CLI commands can invoke Node modules directly, while a loopback handler can validate a request and invoke those same operations. This is an architectural inference, not a guarantee supplied by either framework. In Start, code is isomorphic by default unless constrained; keep Node filesystem/project operations on the server side so they do not enter client bundles. Start's middleware can enforce request checks, but its own documentation says each server function/route that reads or mutates private data still needs authorization at that endpoint; route-level UI guards are not the data boundary. [Start execution model](https://tanstack.com/start/latest/docs/framework/react/guide/execution-model) · [Start server functions/security](https://tanstack.com/start/latest/docs/framework/react/guide/server-functions)

## Package assets, RDF resources, and upgrades

npm's `files` allowlist controls files included in the published package. Including compiled CLI/server files, Vite `dist`, and the release's RDF/SHACL/design resources therefore supports offline reads from the installed package. Node ESM modules expose `import.meta.url`; Node documents resolving a module-relative resource with `new URL('./data.proto', import.meta.url)`. `fileURLToPath` and `node:path` provide platform-specific paths where needed, rather than relying on the current working directory. [npm `files`](https://docs.npmjs.com/files/package.json/) · [Node 24 ESM](https://nodejs.org/download/release/v24.21.0/docs/api/esm.html) · [Node 24 URL API](https://nodejs.org/download/release/v24.21.0/docs/api/url.html) · [Node 24 path API](https://nodejs.org/download/release/v24.21.0/docs/api/path.html)

The repository's approved starter contract already says application upgrades do not change a project's locked vocabulary, shapes, or design; bundled-source updates are explicit and use the preview/impact process. It also records exact acquired bytes and makes stale previews fail on revision mismatch. Thus package upgrade and project-resource update are separate actions; the latter's web preview/accept/commit transport must preserve the captured bytes and expected revisions. That transport detail is issue 13's scope, not an npm or framework feature. ## Local server lifecycle

Node 24's `child_process.spawn()` supports detached launch on Windows, macOS, and Linux, with platform-specific behavior: Windows gives the child its own console window; on non-Windows systems it creates a new process group and session. `subprocess.unref()` lets the parent event loop exit independently. For a long-running process to survive parent exit, Node documents configuring stdio so it is not connected to the parent (for example `ignore` or log files); inherited stdio keeps it attached to the controlling terminal. Default stdio uses pipes that the parent must consume because full pipes can block the child. [Node 24 child-process API](https://nodejs.org/download/release/v24.21.0/docs/api/child_process.html)

These APIs establish a feasible detached-process mechanism, not a reconnectable terminal. Node configures stdio when spawning and documents detaching at launch; it does not document transferring the original TTY to a later CLI process. A background process that can be reconnected to for status/control/logs therefore needs an app-owned channel and log source (such as the already-running HTTP server plus retained/tailable logs). That is an architecture inference. Native terminal reattachment would require a separate terminal/PTY design. The requested foreground default, foreground-to-background transition, and reconnect experience remain product decisions; `detached`/`unref` alone do not settle them.

## Loopback authentication and browser boundaries

A loopback bind limits direct network reachability, but a hostile page can use the victim's browser to issue requests to local services; DNS rebinding can make an attacker-controlled name resolve to a local target while the browser treats requests as the attacker's origin. MITRE CAPEC lists rejecting a malicious `Host` header as a mitigation. Check the request's `Host` against the server's expected loopback host and port, and validate browser `Origin` against the served origin (scheme, host, and port); do not use permissive CORS as the guard. Browser `Origin` may be absent or `null` in some request classes, so mutations should fail closed when the expected browser-origin signal is missing. [MITRE CAPEC-275](https://capec.mitre.org/data/definitions/275.html) · [MDN Origin](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin) · [MDN Host](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Host) · [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

Use a bearer token on API requests in `Authorization: Bearer …`; RFC 6750 recommends that header and says bearer tokens should not be passed in page URLs. A fragment is processed by the user agent before dereference, so it is not sent in the HTTP request, and RFC 9110 forbids fragments in `Referer`. However, the fragment remains in the browser's current URL/history until client code removes it, so these facts do not make a long-lived token in a pasted URL safe. If fragment bootstrap is considered, the defensible pattern is a short-lived, one-use bootstrap value, exchanged immediately and removed from the URL; the resulting session secret stays client-side and accompanies API calls in the Authorization header. This is a security inference from the standards, not a selected decision. [RFC 6750 §§2.1, 5.3](https://www.rfc-editor.org/rfc/rfc6750.html) · [RFC 3986 §3.5](https://www.rfc-editor.org/rfc/rfc3986.html#section-3.5) · [RFC 9110 §10.1.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.1.3)

CORS controls whether browser JavaScript can read a cross-origin response; simple form requests can still be sent cross-origin, so CORS alone is not write authorization. A required non-cookie bearer header plus exact Origin/Host checks protects API writes at the HTTP boundary; the shared project operation/file transaction must still enforce path confinement and revision checks. Chrome 142 added permission prompts for public-site requests to local/loopback destinations, but browser-level Local Network Access is a browser-dependent defense and does not replace the server checks. [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS) · [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) · [Chrome Local Network Access](https://developer.chrome.com/blog/local-network-access) · [transaction contract, issue 10](../issues/10-file-transaction-boundary.md)
