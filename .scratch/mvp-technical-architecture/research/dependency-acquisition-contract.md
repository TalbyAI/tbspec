# Dependency acquisition and RDF import contract research

Checked 2026-10-03 against official Git and Node documentation and first-party RDF package/source metadata. This is planning evidence for issue 12, not an implementation or execution proof. The settled baseline remains Node 24 and N3 2.7.12 for Turtle/N-Triples; issue 11 pins the P-Plan ontology source at commit `773007a6d7ed2fb0054967008cc128fa5c48ca36`.

## Git facts and a bounded acquisition shape

Git normally checks out the remote's active branch during `clone`; `--no-checkout` suppresses that step, and `--bare` implies it. A bare object database can therefore acquire objects without constructing a working tree. `fetch` accepts explicit refspecs, including a fully spelled object ID, and `--no-tags` disables automatic tag following. An omitted fetch refspec instead uses remote configuration, and a clone with no explicit branch uses the remote's active branch. The documentation permits requesting an object ID but does not promise every server will serve an unadvertised or unreachable object ID. [git-clone](https://git-scm.com/docs/git-clone), [git-fetch](https://git-scm.com/docs/git-fetch)

Fetching a commit does not itself materialize its files. `git ls-tree` enumerates tree entries; `git cat-file blob <oid>` emits the blob content, while the distinct `--filters` option asks Git to apply working-tree filters. This gives a path to copy and hash the exact committed blob bytes without checkout transformations. Store the selected commit and tree IDs in the lock, then independently SHA-256 each included byte stream in the project snapshot. Git repository object IDs can use different hash formats, so record the object format with the IDs or treat the IDs as opaque values. [git-ls-tree](https://git-scm.com/docs/git-ls-tree), [git-cat-file](https://git-scm.com/docs/git-cat-file), [git-init](https://git-scm.com/docs/git-init)

Skipping checkout also skips checkout-triggered smudge filters. That matters for Git LFS: Git stores a small pointer blob, while the large object lives on an LFS server; the LFS smudge filter normally downloads it as a file is checked out. A raw tree/blob snapshot therefore contains the pointer, not the payload. Until a separate explicit LFS policy exists, detect LFS pointers and report them as unsupported rather than treating the pointer bytes as the resource. [Git LFS specification](https://github.com/git-lfs/git-lfs/blob/main/docs/spec.md), [Git LFS manual](https://github.com/git-lfs/git-lfs/blob/main/docs/man/git-lfs.adoc)

Do not infer that a bare fetch cannot run hooks. Git documents `reference-transaction` as running for commands that update references, and `core.hooksPath` selects the hook directory. Use an app-owned empty hooks directory for every Git command in the temporary bare repository. `--no-recurse-submodules` explicitly disables submodule fetching; do not run `submodule update`. [githooks](https://git-scm.com/docs/githooks), [git-fetch](https://git-scm.com/docs/git-fetch), [git-submodule](https://git-scm.com/docs/git-submodule)

Git's protocol defaults mark `https`, `ssh`, and `git` as always allowed, `ext` as never allowed, and other protocols (including `file`) as `user`. For an application allowlist, set the default to `never`, then allow only HTTPS and SSH; accept a local repository path as a separate explicit source kind. If `file://` URLs are supported, enable that protocol only for the explicit local-source operation. Unknown `<transport>://` URLs can cause Git to invoke a `git-remote-<transport>` helper, so reject unsupported schemes instead of relying on helper availability. These controls constrain Git's transport selection; they do not sandbox Git, SSH, credential programs, or the host process. [git-config protocol.allow](https://git-scm.com/docs/git-config#Documentation/git-config.txt-protocolallow), [gitremote-helpers](https://git-scm.com/docs/gitremote-helpers)

Node 24's `child_process.spawn(command, args, options)` accepts an argument array and defaults `shell` to `false`; its default environment is `process.env`, and a missing command emits `ENOENT`. Use a resolved Git executable, fixed subcommands, an argument array, and `shell: false`; validate source URLs and refs as Git arguments as well as avoiding shell concatenation. Build a deliberate environment and one-shot Git configuration for the temporary repository, while explicitly retaining any approved SSH/authentication inputs required for private sources. A missing Git executable should produce an actionable error for a requested Git source; it should not silently omit or float that dependency. [Node.js v24 child_process](https://nodejs.org/download/release/v24.20.0/docs/api/child_process.html)

**Planning recommendation (inference):** On an explicit add/update action, fetch one validated source and one explicit selected ref into a private ref in a temporary bare repository, with tags and submodule recursion disabled. Resolve the fetched ref to a commit, compare it with the lock's expected commit when replaying, record its tree ID, enumerate that tree, and copy only the permitted resource closure through raw blob reads. Avoid using remote `HEAD` as an ongoing selector: if the UI allows an omitted branch on first add, resolve the advertised default once during that action, then lock the resulting commit and tree. If a pinned commit cannot be fetched, report that resolution failure; do not substitute the current branch tip. Resolve and parse dependencies only as part of explicit dependency actions; queries and validation can use the recorded local snapshot offline.

## RDF/XML requirement and parser evidence

The pinned P-Plan `.owl` file is RDF/XML. Its first-party bytes begin with an XML declaration and a `DOCTYPE` containing **internal** namespace-entity declarations (`terms`, `prov`, `vann`, `owl`, `xsd`, `rdfs`, `rdf`); the root also sets `xml:base="http://purl.org/net/p-plan"`. Thus extension-based inference alone is not the evidence, and rejecting all DOCTYPE declarations would reject this pinned source unless its entities were first handled equivalently. [Pinned P-Plan source](https://raw.githubusercontent.com/dgarijo/Vocabularies/773007a6d7ed2fb0054967008cc128fa5c48ca36/P-PLAN/p-plan.owl)

The direct `rdfxml-streaming-parser` API is small: `RdfXmlParser` is a Transform stream that accepts supplied chunks or a supplied stream and emits RDF/JS quads. Its constructor accepts `baseIRI`; source code uses that value as the initial base and resolves relative values, while in-document `xml:base` updates the active base. The current first-party manifest says `rdfxml-streaming-parser@3.3.0`, MIT, and lists its own RDFJS-oriented dependencies. This package's RDF/JS output and the existing N3 store API align at the interface level; no integrated N3 2.7.12 + RDF/XML 3.3.0 production proof was run here. [Parser README](https://github.com/rdfjs/rdfxml-streaming-parser.js/blob/master/README.md), [parser source](https://github.com/rdfjs/rdfxml-streaming-parser.js/blob/master/lib/RdfXmlParser.ts), [3.3.0 manifest](https://github.com/rdfjs/rdfxml-streaming-parser.js/blob/master/package.json)

`rdf-parse@5.0.0` is also viable: its documented `rdfParser.parse(stream, { contentType, baseIRI })` consumes a caller-provided stream and emits RDF/JS quads, and it maps `application/rdf+xml` plus `.owl` to the RDF/XML parser. Its current README catalogs many additional formats and actors, including JSON-LD. That broader dispatcher is useful if format discovery is a requirement; it is not necessary for a fixed three-format contract. Supplying a byte stream and an exact allowlisted `contentType` does not require opening a URL through the parser. [rdf-parse README](https://github.com/rubensworks/rdf-parse.js/blob/master/README.md), [5.0.0 manifest](https://github.com/rubensworks/rdf-parse.js/blob/master/package.json)

**Entity/network evidence is limited.** The RDF/XML parser source handles a DOCTYPE callback by extracting simple quoted internal entity declarations and placing them in the SAX parser's entity table, which is sufficient in form for the pinned P-Plan file. That source does not expose a documented external-resource resolver. However, the reviewed package documentation/source does not establish whether external declarations are rejected, ignored, or resolved by the SAX dependency, nor does it establish expansion/resource limits. Do not call either candidate XXE-safe or bounded on this evidence. Before general untrusted RDF/XML support, require a focused acceptance/security check showing that external SYSTEM/PUBLIC entities cannot access files or networks and that internal expansion is bounded, while retaining the pinned file's internal entities. [parser `onDoctype` source](https://github.com/rdfjs/rdfxml-streaming-parser.js/blob/master/lib/RdfXmlParser.ts), [saxes dependency manifest](https://github.com/rdfjs/rdfxml-streaming-parser.js/blob/master/package.json)

## Smallest supported import recommendation

**Planning recommendation (inference):** Keep `N3.Parser` with explicit `text/turtle` and `application/n-triples` formats and add direct `rdfxml-streaming-parser@3.3.0` for `application/rdf+xml`. Keep exact original bytes as the snapshot/hash input, pass them as a stream to the parser, and separately record/pass the stable source IRI as `baseIRI`; let in-document `xml:base` apply according to RDF/XML. Use a strict media-type allowlist and one parser selected by the declared format. This adds one narrowly scoped parser to the settled stack and avoids enabling broad format dispatch for formats the contract has not selected. Pin the package and lockfile transitives; the API/type overlap is compatibility evidence, not proof that the pinned integration works in production.

No parser integration, external-entity exploit test, Git acquisition, or production support claim was executed in this research pass.
